# Interactive C Learning System — 프로젝트 계획 및 타당성 평가

- 작성일: 2026-09-28 (Asia/Seoul)
- 문서 버전: 1.0
- 상태: 구현 전 계획안
- 범위: 기능·데이터·운영 조건의 명세. 애플리케이션 코드 작성과 배포는 수행하지 않는다.

## 1. 프로젝트 개요

### 1.1 목적

사용자가 C언어로 문제를 해결하고 자신의 코드를 설명하면, AI가 코드·설명·학습 목표를 비교하여 피드백을 제공하는 웹 기반 학습환경을 구축한다. 단순 정답 판정에 그치지 않고 사용자의 의도, 개념 이해, 독립적인 문제 해결 능력을 관찰한다.

핵심 학습 흐름은 다음과 같다.

1. 사용자 배경과 학습 목적을 확인한다.
2. AI가 목표를 질문하고 사용자가 목표를 제시한다.
3. AI와 사용자가 현재 수준에 맞는 과제와 완료 기준을 확정한다.
4. 사용자가 코드를 작성·제출한다.
5. AI가 질문하고 사용자가 코드의 의도와 동작을 설명한다.
6. AI가 코드·설명·목표의 일치 여부를 평가한다.
7. 사용자가 수정하고 필요한 경우 재평가한다.
8. 세션 종료 시 학습 수준을 갱신하고 진행상황을 저장한다.

### 1.2 초기 범위와 설계 가정

| 항목 | 초기 계획 |
| --- | --- |
| 학습 언어 | C언어. 기본 언어 기준은 C17로 제안한다. |
| 사용 형태 | 개인 사용용 웹 화면과 로컬 백엔드를 제안한다. 공개 서비스는 후속 범위이다. |
| 평가 방식 | 코드와 설명을 읽고 추론하는 AI 평가 |
| 실행 기능 | 컴파일·실행·Online Judge·격리 환경을 구현하지 않는다. |
| AI 연결 | 사용자 API 키를 이용한 OpenAI API 연결 |
| 저장 | 사용자가 내보내고 불러올 수 있는 JSON 파일 |
| 초기 성공 기준 | 최초 설문부터 평가·수준 갱신·저장·복원까지 한 세션을 완결한다. |

로컬 백엔드, C17, 아래의 수준 분류는 원문의 필수조건을 구체화한 설계 제안이다. 특정 프런트엔드 프레임워크, 모델, 공개 배포 방식은 아직 확정하지 않는다.

### 1.3 해석 원칙

- 목표는 사용자에게서 얻고 AI가 구체화한다. 사용자가 목표를 떠올리기 어려워하면 AI가 후보를 제안한다.
- AI가 갱신하는 메타데이터는 추정 숙련도·취약 개념·권장 난이도이다. 학력·학습 목적 등 사용자 제공 사실은 사용자가 변경한다.
- 학력은 설명 방식의 참고 자료이며 실력 판정의 대체물이 아니다.
- 실행하지 않은 코드를 테스트 통과 또는 실행 검증 완료로 표시하지 않는다.
- 정지조건은 개발 작업에 적용한다. 학습자가 제출한 연습 코드의 오류는 원칙적으로 평가 대상이다. 다만 그 오류가 앱의 실행·렌더링·저장 경로를 통해 실제 보안 취약점을 발생시키는 경우에는 보안 정지조건을 적용한다.

## 2. 구현 요구 사항

### 2.1 반드시 구현되어야 할 조건

아래의 필수조건은 원문에서 직접 요구한 기능과 해당 기능을 일관되고 안전하게 동작시키기 위한 최소 보완 조건으로 구성한다.

#### MUST-01. 초기 설문 및 사용자 프로필

- 학습 배경, 코딩 경험, 학습 목적, 자기평가, 설명 선호, 세션 가용 시간을 질문한다.
- 학력 등 불필요한 개인정보는 응답을 생략할 수 있게 한다. 학교명·실명은 필수로 요구하지 않는다.
- 사용자 제공 정보와 AI 추정 정보를 분리한다.
- 관찰 근거가 없는 개념은 ‘미평가’로 기록한다.
- 설문과 실제 코드·답변의 근거를 이용해 초기 난이도를 설정한다.

완료 기준: 최초 사용자가 프로필을 만들고, AI가 해당 프로필을 반영한 첫 과제를 제안할 수 있다.

#### MUST-02. 사용자 목표와 과제 확정

- AI는 사용자가 배우거나 구현하고 싶은 목표를 말하도록 질문한다.
- 과제에는 목표, 입력 조건, 요구 동작, 허용·제한 사항, 완료 기준을 포함한다.
- 사용자와 합의한 과제 기준을 세션에 저장한다.
- 진행 중 목표를 바꾸면 변경 이력을 남기고 이후 평가에 적용할 기준을 명확히 한다.
- 사용자의 수준과 가용 시간에 비해 큰 목표는 작은 과제로 나눈다.

완료 기준: 사용자가 무엇을 작성하고 어떤 기준으로 평가받는지 제출 전에 확인할 수 있다.

#### MUST-03. 코드 작성 및 제출 버전 관리

- C 코드 편집과 제출 기능을 제공한다.
- 작성 중인 코드와 제출 코드를 분리한다.
- 제출할 때 코드 버전 ID와 제출 시각을 저장한다.
- 질문·답변·평가는 해당 제출 버전과 연결한다.
- 초기 버전에서는 사용자 코드를 컴파일하거나 실행하지 않는다. 외부 실행 도구로 우회 실행하는 기능도 포함하지 않는다.

완료 기준: 제출 후 편집하더라도 AI가 평가하는 코드 사본은 변경되지 않는다.

#### MUST-04. 설명을 유도하는 질의응답

- 사용자에게 접근 방식, 변수의 의미, 조건과 반복의 역할, 경계 조건 등을 설명하도록 질문한다.
- 한 번에 핵심 질문 1~2개를 제시하는 것을 기본으로 한다.
- 코드에서 의심되는 부분을 찾았을 때 사용자의 사고 과정을 확인하는 질문을 우선한다.
- 힌트 사용 여부와 도움의 정도를 기록한다.
- 설명과 코드가 어긋나면 해당 위치와 답변을 연결하여 추가 질문한다.
- 정답 전체를 먼저 제공하는 것을 기본 동작으로 삼지 않는다. 사용자가 해설을 요청하면 제공하고 도움 이력에 반영한다.

완료 기준: 최초 코드 제출만으로 이해도를 확정하지 않고, 사용자 답변을 반영해 평가를 보완한다.

#### MUST-05. 근거 기반 AI 평가

| 평가 항목 | 확인 내용 |
| --- | --- |
| 목표 충족 | 확정한 요구사항을 구현했는가 |
| 논리적 타당성 | 조건·반복·상태 변화가 의도에 부합하는가 |
| C언어 이해 | 타입·범위·수명·포인터 등을 적절히 이해하는가 |
| 의도와 구현의 일치 | 설명한 동작과 실제 코드의 의미가 일치하는가 |
| 설명 능력 | 동작 과정과 주요 선택의 이유를 설명하는가 |
| 경계 조건 이해 | 입력 범위와 예외적인 조건을 고려하는가 |
| 독립 해결 정도 | 어느 정도의 도움을 받아 해결했는가 |

- 항목별 판정은 ‘충족 / 일부 충족 / 미충족 / 판단 보류’로 표현한다.
- 판정에는 코드 버전·줄 번호 또는 답변 등 근거, 이유, 다음 행동, 확신도를 포함한다.
- 확신도는 AI의 자기평가이며 통계적으로 보정된 정확도 확률로 표현하지 않는다.
- 실행하지 않았음을 평가 화면에 표시한다.
- 정보가 부족하면 추가 질문하거나 판정을 보류한다.
- 구현체 의존 동작이나 정의되지 않은 동작이 있으면 가정과 한계를 명시한다.
- 사용자의 설명이 짧다는 이유만으로 개념을 모른다고 단정하지 않는다.

완료 기준: 코드·설명·목표의 불일치를 근거와 함께 제시하고, 판단 불가능한 항목을 구분한다.

#### MUST-06. 수정 반복 및 세션 상태 관리

- ‘목표 설정 → 과제 확정 → 작성 → 설명·질문 → 평가 → 수정 → 종료’의 상태를 명시적으로 관리한다.
- 중간 저장·재개와 사용자 요청에 따른 조기 종료를 지원한다.
- 조기 종료 시 완료 여부와 실제 관찰 범위를 구분한다.
- AI는 상태 변경을 제안하고 프로그램이 허용된 전환인지 검증하여 확정한다.
- 평가 요청 도중의 중복 제출과 이미 반영한 결과의 재반영을 방지한다.

완료 기준: 수정 전후 평가가 혼동되지 않으며, 중단한 단계와 미답변 질문을 복원할 수 있다.

#### MUST-07. OpenAI API 연결 및 키 관리

- 사용자는 자신의 API 키를 입력한 뒤 AI 학습을 시작한다.
- 제안하는 초기 방식은 로컬 백엔드 시작 설정에서 키를 입력하고 백엔드가 API를 호출하는 구조이다.
- 키를 프런트엔드 소스, 번들, 학습 JSON, 프롬프트, 브라우저 영구 저장소, 일반 로그에 포함하지 않는다.
- 초기 버전에서 백엔드는 키를 실행 중 메모리에만 보관하며 종료 후 재입력한다.
- 로컬 백엔드는 루프백 주소에만 바인딩하고 허용 출처·호스트·요청 인증을 확인한다. CORS 설정만으로 인증을 대체하지 않는다.
- 키가 없거나 유효하지 않아도 기존 파일 열람·코드 편집·저장은 가능하게 한다.
- 시간초과, 인증 실패, 요청 제한, 연결 오류를 구분하고 기존 작업을 보존한다.
- 요청 크기·출력 길이·재시도 횟수에 상한을 두고 무한 재시도를 방지한다.
- 코드·답변·필요한 프로필이 외부 API로 전송됨을 시작 전에 알리고 불필요한 개인정보는 전송하지 않는다.

완료 기준: 정상 키로 대화가 가능하고, 실패 시 코드가 유지되며, 저장 파일과 로그에서 키가 노출되지 않는다.

#### MUST-08. 자동 프롬프트 및 응답 검증

자동 입력은 다음 요소로 구성한다.

1. 고정 교육 지침과 평가 제한.
2. 사용자 학습 목적·수준·설명 선호.
3. 현재 목표·과제 조건·세션 단계.
4. 제출 코드·답변·힌트·수정 이력 중 필요한 근거.
5. 질문·평가·프로필 변경 제안의 출력 형식.

- 세션 시작, 복원, 후속 요청에서 필요한 지침과 상태를 재구성한다.
- 긴 이력을 요약할 수 있지만 현재 과제, 평가 대상 코드, 미답변 질문, 평가 근거는 보존한다.
- 코드·주석·답변·불러온 JSON의 내용은 분석 대상 데이터로 취급한다.
- 불러온 파일이 고정 지침이나 보안 정책을 덮어쓰지 못하게 한다.
- 구조화된 응답을 받고 형식, 필수 필드, 코드 참조, 허용된 변경 범위를 검증한다.
- 구조화 실패·거절·응답 중단 시 불완전한 결과로 상태나 수준을 갱신하지 않는다.
- AI 출력과 사용자 입력을 화면에 표시할 때 임의 HTML·스크립트가 실행되지 않도록 처리한다.

완료 기준: 잘못된 응답은 안전하게 거부되며, AI 출력만으로 파일 접근·명령 실행·임의 상태 변경이 발생하지 않는다.

#### MUST-09. JSON 저장 및 불러오기

| 저장 영역 | 내용 |
| --- | --- |
| 파일 정보 | 스키마 버전, 저장 시각, 앱 버전 |
| 사용자 프로필 | 사용자 제공 사실, AI 추정 수준, 평가 근거 |
| 세션 | ID, 목표, 요구사항, 진행 단계, 완료·중단 여부 |
| 코드 | 작성 중 코드, 제출 버전, 제출 시각 |
| 대화 | 질문·답변, 연결된 코드 버전 |
| 평가 | 판정, 근거, 불확실성, 평가 대상 |
| 학습 이력 | 힌트 사용, 수정 과정, 프로필 변경 전후 값 |
| 재개 정보 | 미답변 질문, 다음 행동, 요청 완료·반영 여부 |
| 비밀이 아닌 설정 | 언어 기준, 모델명, 프롬프트 버전 |

- 저장 버튼으로 JSON 파일을 내보내고 불러오기 버튼으로 복원한다.
- 파일 자체로 재개할 수 있게 하며 API 서버에 보관된 대화 ID에만 의존하지 않는다.
- 파일 형식·크기·자료형·필수 필드·버전·참조 관계를 검증한다.
- 검증 실패 시 현재 상태를 덮어쓰지 않는다.
- 미저장 작업이 있을 때는 교체 전에 알린다.
- 진행 중 요청을 저장한 경우 결과 미확정 상태로 복원한다. 자동 재요청이나 중복 수준 갱신을 하지 않는다.
- 복원은 저장 시점의 학습 상태 복원을 뜻한다. 이후 AI 응답의 문구까지 동일하게 재현하는 것은 보장하지 않는다.

완료 기준: 앱을 닫고 다시 열어 같은 코드·목표·질문·진행 단계에서 이어갈 수 있다.

#### MUST-10. 종료 평가 및 메타데이터 갱신

- 개념별 수준을 ‘미평가 / 입문 / 연습 중 / 독립 적용 / 응용’으로 관리한다.
- 단일 정답만으로 숙련을 확정하지 않고 설명, 도움의 정도, 관찰의 일관성을 반영한다.
- AI는 수준·취약 개념·권장 과제 변경안을 생성한다.
- 프로그램은 허용된 필드와 근거를 검증한 뒤 반영한다.
- 학력·목적 등 사용자 제공 사실은 AI가 임의로 바꾸지 않는다.
- 변경 전후 값과 이유를 보관하고 사용자에게 보여준다.
- 관찰이 부족하면 기존 수준을 유지하고 추가 평가 필요를 기록한다.
- 사용자에게 평가 정정 요청 수단을 제공한다.

완료 기준: 세션 종료 후 근거 있는 수준 변화가 다음 세션에 반영되며, 사실 정보가 임의 변경되지 않는다.

#### MUST-11. 최소 화면 구성

| 화면 | 필수 요소 |
| --- | --- |
| 시작 | 새 학습, JSON 불러오기, API 연결 상태 |
| 프로필 | 초기 설문, 현재 프로필 확인·사실 정보 수정 |
| 학습 | 목표, 편집기, 대화, 제출·힌트·저장·종료, 평가 대상 버전 |
| 결과 | 항목별 평가, 근거, 수준 변화, 다음 학습 제안 |

완료 기준: 개발 도구를 조작하지 않고 화면을 통해 학습과 저장·복원을 수행할 수 있다. 백엔드 시작·키 설정은 별도 초기 설정으로 안내한다.

### 2.2 선택 구현 조건

다음 기능은 필수 학습 흐름이 완성된 이후 추가한다. 선택 기능이 없다는 이유로 초기 버전의 완료를 막지 않는다.

| OPT-03 | 자동 임시 저장·복구 알림 | 수동 JSON 저장·복원 완성 후 |

| 단계 | 작업 | 통과 기준 |

## 3. 정지조건

### 3.1 프롬프트를 이해할 수 없는 경우

목표·대상·요구 동작을 신뢰할 수 있게 해석하지 못하거나, 서로 다른 해석이 핵심 기능을 바꾸는 경우 작업을 멈추고 확인한다. 단순한 문장 표현 차이 또는 결과에 영향이 없는 구현 세부사항은 이 조건으로 보지 않는다.

보고 내용: 이해하지 못한 문장, 가능한 해석, 결정에 필요한 최소 질문.

### 3.2 요구사항 사이의 모순을 발견한 경우

동시에 충족할 수 없는 조건이 확인되면 작업을 멈춘다. 어느 한 조건을 임의로 삭제하거나 선택 조건으로 낮추지 않는다.

보고 내용: 충돌하는 조건, 동시 충족이 불가능한 이유, 가능한 수정안과 영향 범위.

### 3.3 구현에서 보안 취약점을 발견한 경우

실제 설계·구현·실행 경로에서 보안 취약점을 발견하면 즉시 작업을 멈추고 보고한다. 예시는 다음과 같다.

- API 키가 소스·로그·저장 파일·프런트엔드 자산으로 노출됨.
- 허가되지 않은 요청으로 API 호출이나 학습 데이터 접근이 가능함.
- AI 출력·사용자 입력·JSON 내용이 임의 스크립트 또는 명령으로 실행됨.
- 파일 불러오기로 보안 정책이나 허용되지 않은 시스템 상태를 바꿀 수 있음.

보고 내용: 취약점의 위치, 확인 근거, 영향 범위, 노출된 정보의 종류, 권장 수정안. 비밀값 자체는 보고에 포함하지 않는다.

위험이 있을 수 있다는 일반적인 가능성과 확인된 취약점을 구분한다. 계획 단계에서 아직 발생하지 않은 위험에 대한 예방책을 정하는 것 자체를 취약점 발견으로 간주하지 않는다.

### 3.4 정지 후 처리와 재개

- 중단 사유와 마지막 정상 상태를 기록한다.
- 상태 보존에 비밀 유출 등 추가 위험이 없다면 진행 내용을 보존한다.
- 문제를 우회하여 구현·배포를 계속하거나 관련 요구사항을 임의 변경하지 않는다.
- 필요한 명확화·충돌 해소·수정 방향에 대한 사용자 확인을 받은 뒤 재개한다.
- 보안 문제는 합의된 수정 후 재검증을 거쳐 다음 단계로 진행한다.

API 시간초과나 손상된 JSON처럼 예상한 입력·운영 오류는 해당 요청을 실패 처리하고 기존 상태를 보존한다. 그 자체로 개발 작업 전체의 정지조건은 아니지만, 모순이나 보안 취약점의 증거가 발견되면 위 조건을 적용한다.

## 4. 계획의 타당성 평가

### 4.1 종합 판단

개인용 C언어 학습 MVP로서 조건부로 타당하다. 실행 환경을 제외하여 초기 구현 범위를 줄이고, 질문과 설명을 통해 사용자의 이해를 확인한다는 목적이 기능 구조에 일관되게 반영되어 있다. 다만 요구사항이 충족되도록 설계되었다는 것과 AI의 교육 효과·평가 정확성이 입증되었다는 것은 구분해야 한다.

### 4.2 평가 항목별 판단

| 항목 | 판단 | 근거와 한계 |
| --- | --- | --- |
| 원문 충족 | 설계상 충족 | 7개 필수조건, C언어 범위, 3개 정지조건에 대응한다. 실제 충족은 구현 검증이 필요하다. |
| 기술적 실현 가능성 | 높음 | 웹 편집·대화·API·JSON으로 구성되며 사용자 코드 실행 기반시설이 필요하지 않다. |
| 교육 설계 | 합리적 가설 | 코드 설명과 질문은 이해를 관찰할 기회를 준다. 실제 학습 개선은 사용자 관찰로 확인해야 한다. |
| 평가 신뢰성 | 제한적 | 모델이 C의 의미를 오판하거나 그럴듯한 설명을 과대평가할 수 있다. 판단 보류·근거 표시·고정 사례 검증이 필요하다. |
| 개인화 | 조건부 타당 | 사용자 사실과 추정 수준을 분리하여 과도한 단정을 줄인다. 초기에는 근거가 부족하다. |
| 저장·복원 | 높음 | 상태와 근거를 파일에 포함하면 API의 대화 보관에 의존하지 않는다. 버전·참조 검증이 필요하다. |
| 보안 구조 | 예방책을 포함한 설계안 | 백엔드 키 관리와 입력 검증을 계획했다. 구현물이 없어 취약점 부재는 검증하지 않았다. |
| 개발 범위 | 관리 가능 | 단일 언어·개인용·실행 제외 조건을 유지해야 한다. 공개 서비스 전환은 별도 설계가 필요하다. |
| 비용·응답 지연 | 아직 미확정 | 모델, 요청 길이, 질문 횟수에 좌우된다. 실제 사용량을 측정해야 한다. |

### 4.3 원래 계획에서 구체화한 부분

1. ‘메타데이터 수정’의 범위를 AI 추정 정보로 한정하여 학력·목적의 임의 변경을 방지했다.
2. 목표 제시의 주체를 사용자로 명확히 하고 AI는 구체화와 조정을 맡도록 했다.
3. 실행 검증과 추론 평가를 구분하여 실제로 확인하지 않은 정확성을 보장하지 않도록 했다.
4. 코드 버전과 평가 근거를 연결하여 편집 중 평가 대상이 바뀌는 문제를 방지했다.
5. JSON 복원에 미답변 질문·요청 상태·프로필 변경 이력을 포함했다.
6. 정지조건의 적용 대상을 개발 작업으로 명시하여 연습 코드의 오류 피드백과 구분했다.
7. 중복 응답과 불완전한 응답이 수준 갱신으로 이어지지 않도록 반영 규칙을 추가했다.

### 4.4 구현 시작 전에 확정할 결정

| 결정 항목 | 현재 제안 | 필요한 결정 이유 |
| --- | --- | --- |
| 실행 형태 | 개인용 로컬 웹+백엔드 | 키 입력 위치와 배포·인증 범위를 결정한다. |
| C언어 기준 | C17 | 문법·표준 라이브러리·구현체 의존 설명의 기준이 된다. |
| 모델 | 미선정 | 구조화 응답 지원, 코드 평가 품질, 비용·지연을 비교해야 한다. |
| 수준 갱신 기준 | 여러 근거를 이용한 보수적 갱신 | ‘독립 적용’으로 올리는 데 필요한 관찰 기준을 정해야 한다. |
| 요청 제한 | 크기·출력·재시도에 유한 상한 | 개발 시 구체적인 수치를 정해야 한다. |
| 평가 품질 기준 | 고정 사례와 반복 평가 | 허용할 오판, 근거 누락, 판정 변동의 기준을 정해야 한다. |

위 항목은 현재 계획을 작성하지 못할 정도의 모순은 아니다. 다만 해당 기능을 구현하기 전에는 결정해야 하며, 결정 과정에서 원문과 충돌하면 정지조건을 적용한다.

### 4.5 검증의 범위

이 문서는 요구사항의 논리적 일관성과 구현 구조를 평가한 결과이다. 코드 실행, API 실제 연결, 보안 점검, 학습 효과 실험은 수행하지 않았다. 따라서 구현 완료, 보안 인증, 교육적 효과 입증을 의미하지 않는다.
